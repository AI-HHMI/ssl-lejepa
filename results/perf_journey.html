What we changed, and why

  1. Measure first: a benchmark window, a profiler, and tokens/s
    Every run does 10 warmup steps, then an unprofiled 50-step timed window, then a short profiled window with named phases (01_DATA_IO … 06_OPTIMIZER). Results are JSON-lines per run, tied to the git commit and diff. We switched the main metric from samples/s and Mvox/s to tokens/s once changes to the patch embedding and view scheme started changing how many tokens each sample produces.
    Baseline: fp32, 267 ktok/s on one B300. The profile showed attention running on an fp32 "memory-efficient" kernel, about 64% of GPU time.
  2. bf16 autocast
    Forward and loss run under torch.autocast(bfloat16), with SIGReg kept in fp32 because its cos/sin statistics are sensitive to precision. SDPA switched to cuDNN flash-attention kernels, and attention backward went from 1.37 s to 0.18 s over the 3 profiled steps.
    267 → 822 ktok/s (batch 84), 3.1×.
  3. torch.compile on the encoder
    Views change shape every step, so padding caused a recompile for each divisibility pattern. We made crops multiples of the patch size and compiled with dynamic=True. Inductor fuses the autocast casts, layernorm and elementwise ops.
    822 → 935 ktok/s, +14%. The GPU was now only about 60% busy: the data loader couldn't keep up (~170 samples/s with 4 workers).
  4. More data-loader workers
    Throughput stopped at about 170 samples/s whatever the batch size, so the limit was data loading. 8 workers removed the data wait; 16 added nothing.
    935 → 1,333 ktok/s, +43%, 88% GPU busy. The best single-B300 result.
  5. DDP across 8 GPUs
    Added torchrun + DistributedDataParallel. Each rank samples its own data, only rank 0 writes, and tokens are summed across ranks. SIGReg and BatchNorm statistics are still per rank for now.
    8.1M tok/s on 8×B300 = 1,014 per GPU, 76% of the 1-GPU rate.
  6. New setup: H200, hemibrain EB, displace views
    We moved to Gary's hemibrain EB training split (8 nm isotropic) and a displace view scheme: fixed-size globals, with each local placed inside one of its sample's globals. Every step has the same 2 input shapes, and every GPU does identical work. 128³ inputs with 96³/64³ views gave more room for crops to shift.
    H200 1-GPU baseline: 856–881 ktok/s. This is a new baseline, not comparable with the B300 numbers.
  7. Fix the profiler, then CUDA graphs
    Trimming runs to end right after profiling had put the profile in the stretch where data workers had already finished, so it looked ~97% GPU busy. We now give the loader extra batches so workers stay active through the profile. With only 2 static shapes, the encoder can be compiled with mode="reduce-overhead", which replays recorded kernel sequences with CUDA graphs instead of having the CPU launch each kernel.
    881 → 990 ktok/s on one H200 (+12%). At 8 GPUs 649 → 759 (+17%).
  8. Give the 8-GPU job the whole node
    Cutting to 4 workers per GPU was much worse, because LSF gives a job one core per requested slot, so fewer workers also meant fewer cores for the training processes. We now request 12 cores per GPU (all 96 at 8 GPUs), whatever the worker count.
    759 → 812 ktok/s per GPU at 8 GPUs, 6.5M tok/s per node, 83% scaling.
  9. Batch the encoder calls
    Displace views share shapes, so all globals go through the encoder as one batch and all locals as another: 2 calls per step instead of 6. The projector's BatchNorm then pools statistics over each group. CPU-side forward time fell 40–55%, but the GPU was already ~99% busy.
    +3% at 1 GPU (1,023 ktok/s) and at 8 GPUs (835 per GPU).
  10. Ship uint8, normalize on the GPU
    Workers used to hand over float32 samples: ~705 MB per step per GPU through shared memory, a pinned-memory copy and the host-to-device copy, 8 times over on a full node. With miao's defer_image_ops they send the raw uint8 crops (4× smaller), and finish_images casts and normalizes on the GPU. CPU-side backward time at 8 GPUs fell from 460 to 200 ms per step, and ranks stopped waiting on each other at the all-reduce.
    8 GPUs: 805 → 975 ktok/s per GPU, 7.8M tok/s per node, 94% scaling. 1 GPU: +1.4% (1,036).
  11. Count FLOPs: MFU, and wider models
    Each step now logs model training FLOPs from the actual view shapes (6 × params per token, plus attention), TFLOP/s, MFU against the GPU's dense bf16 peak, and peak memory. Width 512 runs at 33% MFU on one H200. Width 768 reaches 38% (larger matmuls) but peaks at 142 GB at batch 84, right at the H200's limit. Width 1024 ran out of memory at batch 84.
    Wider is more efficient per FLOP but costs ~2× per token. The first 6 h training runs use width 512.
  12. Back to B300 with the H200 setup
    We reran the H200 setup (hemibrain 128³, displace views, CUDA graphs, batched views, uint8) on B300. It's fast, but at only 21.5% MFU: B300's peak is 2.3× the H200's, so the same width-512 model uses less of it. Widening helped less than on H200: 768 reached 27%, and 1024 × 64 reached 31% (632 ktok/s). 1024 × 128 did not finish. The profile showed the patch-embedding Conv3d taking ~15–17% of GPU time.
    1 GPU: 1,501 ktok/s. 8 GPUs: 11.5M tok/s per node, 1,437 per GPU, 96% scaling.
  13. Patch embedding as a Linear layer
    A Conv3d with stride equal to its kernel is a matmul in disguise, but cuDNN ran it as slow implicit-GEMM kernels, worst on B300. We cut the volume into 8³ patches with a reshape and apply one nn.Linear. The math is the same, and old Conv3d checkpoints still load.
    B300 width 512: 1,501 → 2,033 ktok/s (1.35×, 29% MFU). H200 width 512: 1,036 → 1,156 (1.12×, 38%). A100 width 768: 242 → 262 (1.08×, 55%).
  14. Pay for correctness: flash attention and an eager patch embed
    Two kernels were quietly wrong. cuDNN's fused attention backward returned NaN gradients on some trained weights: every "divergence" in our long runs (nanhunt_flash). Flash attention avoids it. Inductor's fused patchify kernel for the Linear patch embed corrupted memory under CUDA graphs at some batch sizes, crashing some runs and silently producing NaNs in others (b300-compile). Running the patch embed outside the compiled graph fixes it at no cost (1,425 vs 1,414 ktok/s).
    B300 width 512: 2,033 → 1,425 ktok/s (−30%, 20% MFU), nearly all of it flash attention. H200 loses 12–21%. This is what training runs at now. Re-enabling cuDNN on B300 only, if its kernels prove safe there, would win most of it back.

Dead ends (still useful)

  • Vectorized ViewMaker±0%
    ~2,300 small crop and flip kernels per step became one gather per view. It didn't help, because eager mode was already GPU-bound: those kernels were queued asynchronously behind the model's work.
  • Multiple-of-64 token countswrong guess
    Larger 96³/64³ views are 12% slower per token than 88³/56³: longer sequences make attention cost more per token. The apparent "30% slowdown" that prompted the guess was B300 vs H200.
  • bf16 gradient compression−1%
    Halving the all-reduce bytes didn't change the time. Bandwidth isn't the limit; waiting is.
  • Per-block compile−7% / −11%
    Meant to overlap the all-reduce with backward. Instead it brought back CPU launch overhead (24 graph replays per step plus uncompiled work between blocks).
  • prefetch_factor, 16 workers, f32 matmul modes±noise
    None mattered once their underlying bottleneck was gone.

Lessons

  • Measure GPU busy directly, over the same steps you're analysing. "Kernel time ÷ step time" from different windows misled us twice.
  • A profile is only as representative as the steps it covers. Idle data workers made the node look healthier than it was.
  • Normalize by work actually done. Mvox/s hid a 27% token-count change caused by a padding tweak.
  • Check the hardware before comparing. One queue change (B300 → H200) looked like a 30% regression in the view scheme.
  • Host memory traffic grows with the GPU count. Float32 samples cost nothing on one GPU and 15% of throughput on eight. Ship the smallest dtype the GPU can finish.
  • Repeats agree to within ~1% for the same config on the same GPU type. Earlier "±5–10%" came from comparing runs that differed in more than the knob under test.
  • Profile each new GPU; small layers can dominate. The patch-embedding conv is a tiny share of the FLOPs but took ~15–17% of B300 time. Rewriting it as a Linear gave 1.08× on A100 and 1.35× on B300.
  • Check the loss of every benchmark run, not just its speed. A width-1024 B300 run looked like the best result yet (49% MFU), but its loss was NaN from step 0: a compiled kernel was broken, and it ran fast on garbage.
  • Throughput changes can change training. Rounding crop sizes, dropping padding, and per-rank SIGReg all change what the model learns.

Where the time still goes, and what's next

On one H200 we're GPU-bound: 99% busy at about 38% MFU with the Linear patch embed. Much of the remaining GPU time goes to layernorm, GELU, casts and other memory-bound kernels, which a width-512 model can't hide. Wider models hide it better: width 768 on A100 reaches 55% MFU. At 8 GPUs, scaling is 94–96% now that samples cross the host as uint8. The first two 6-hour training runs (outdir/e00/train6h/) use 8×H200, width 512, EB-only vs. hemibrain crops 002 + 003 (2 Tvox, with EB's validation and test regions cut out). Per-queue default widths and batch sizes are in QUEUE_ARCH in e00_basic.py.

  • Measure 8×B300 with the Linear patch embed. Extrapolating from 96% scaling gives ~15.6M tok/s at width 512. That hasn't been measured yet.
  • Get back the speed the fixes cost. The training "divergence" was cuDNN attention's backward pass returning NaN (e00/nanhunt_flash). Flash attention avoids it but is 12–21% slower on H200 and ~30% on B300. CUDA graphs with the Linear patch embed crash or silently miscompile at some batch sizes (e00/b300-compile), so long runs used dynamic compile until e00/cudagraph-fix confirmed the workaround: running the patch embed outside the compiled graph fixes it at no cost (1,425 vs 1,414 ktok/s at batch 84, B300).
  • Wider models for the next training run: higher MFU, and usually better SSL features. Width 1024 on B300 with flash attention: 619 ktok/s at 30.2% MFU (e00/cudagraph-fix/d1), 0.43× width 512's token rate.
  • Look at the remaining non-matmul kernels (layernorm, GELU, casts) for poorly fused ones.
  • Before relying on multi-GPU results: compute SIGReg statistics across all GPUs and use SyncBatchNorm in the projector. Both are still per GPU.
  • Training recipe: the runs use constant-lr Adam (1e-4) with no warmup, schedule or evaluation. That's fine for a sanity run, not for a final model.
